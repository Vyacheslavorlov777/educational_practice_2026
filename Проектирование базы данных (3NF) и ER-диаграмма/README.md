# Задание 1. Проектирование базы данных (3NF) и ER-диаграмма

## Какие сущности выбраны и зачем

### partners (партнёры)

Хранит данные о партнёрах: название компании, ИНН, контакты, рейтинг.
Нужна для просмотра и редактирования данных партнёров.

* PK: `partner_id`
* Обязательные поля: `company_name`, `inn`
* Необязательные поля: `contact_email`, `phone`, `rating` — в исходных данных
  встречаются пустые значения (например, у ИП Петрова нет телефона).

### products (товары)

Хранит уникальные названия товаров. Вынесена в отдельную таблицу, потому что
одно и то же название товара повторяется в разных отгрузках
(«Стиральный порошок "Альфа"» встречается дважды). Если хранить название
товара прямо в таблице отгрузок, это дублирование данных и нарушение 3NF.

* PK: `product_id`
* `product_name` уникально

### shipments (отгрузки)

Хранит историю отгрузок: кому, какой товар, когда, сколько и на какую сумму.

* PK: `sale_id`
* FK: `partner_id` → `partners`
* FK: `product_id` → `products`

## Как таблицы связаны

* Один партнёр — много отгрузок (1:N через `shipments.partner_id`).
* Один товар — много отгрузок (1:N через `shipments.product_id`).

## Почему структура в 3NF

* **1NF** — каждое поле атомарно, нет списков и повторяющихся групп.
* **2NF** — первичные ключи всех таблиц простые (не составные), поэтому
  частичных зависимостей нет.
* **3NF** — название товара не хранится в `shipments`, а вынесено в
  `products`, поэтому в `shipments` нет полей, зависящих друг от друга —
  только от `sale_id`.

## Как реализована история отгрузок

История отгрузок партнёра — это выборка из `shipments` с фильтром по
`partner_id`, соединённая (`JOIN`) с `products` для получения названия
товара. Пример такого запроса — в
`Разработка проверочных SQL-запросов (Эмуляция бэкенда)/queries.sql`.
